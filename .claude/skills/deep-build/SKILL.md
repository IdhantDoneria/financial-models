# Deep Build

## Why this exists

The pattern that burns time and trust: a fix looks complete, gets shipped, and the *next* prompt — a fresh bug report, a re-audit, a "check the other cases too" — turns up something the fix should have caught the first time. Each round costs real time and, on a live product, real users hitting a live bug. The fix for that pattern isn't more fixing — it's front-loading the thinking that should have happened before the first line of code, staying honest about what you actually know versus assume while you build, and refusing to call something "done" until it's been actively attacked, not just glanced at.

This is not a bureaucratic checklist. It's a sequence of honest questions, asked in order, each one earning the right to move to the next: **do I actually understand this? is what I've been asked to build actually correct? what would break it? does my plan survive that? did it actually survive it? is this actually ready to ship, or does a human need to look at it first?**

## Phase 1 — Understand before touching anything

Before writing or editing a single line, get a real, evidence-based picture of what you're changing — not a plausible-sounding guess, and not an assumption carried over from a similar-looking problem elsewhere.

- **Read the actual code path end to end**, not just the function or file named in the request. Trace it from the real entry point (the API route, the UI event handler, the CLI command, the job trigger) through every layer it passes through, to wherever the result actually lands — a response, a database row, a rendered value, a file on disk. A fix that only touches one link in that chain is a fix that's guessing about the others. In an unfamiliar repo, spend the first few minutes just mapping this chain — grep for the function/route/symbol named in the request, and follow it outward — before touching anything.
- **Find the root cause, not the symptom.** If a value is wrong, ask *why* it's wrong before deciding *how* to fix it. "The parser grabbed the wrong field" and "the parser grabbed the wrong field because the real one lives in a table layout it was never designed to read" are different bugs with different fixes — the second framing is usually the one that's actually true, and it only shows up if you look at the real input that triggered it, not a description of it.
- **Check what's already there.** Grep for existing tests, existing helper functions, and existing comments that explain a prior decision — well-maintained codebases often record *why* something is the way it is right next to the code itself; read that before assuming it was never considered. Re-solving an already-solved problem, or contradicting a documented decision without knowing why it was made, both waste time. This includes idiom, not just logic: if the codebase already has a pattern for the kind of thing you're about to add (a guarded-promise lazy-loader, a shared validation helper, a particular error-handling shape), reuse it rather than inventing a parallel one — consistency is part of correctness in a codebase other people maintain.
- **Use real data, not a synthetic stand-in, whenever it's available.** A committed fixture from a real case, a real API response, a real file the bug was originally reported against — these surface the messy edge cases (malformed input, an unexpected format, a value at a boundary) that a clean example you typed up yourself never will. When the target is a real external system (a live API, a real upstream service), and hitting it is safe and cheap, prefer that over mocking it — a mock only proves your code handles what you assumed the response would look like.
- **When a fact genuinely isn't discoverable in the code, stop and ask instead of inventing something plausible.** Some things are not technical facts waiting to be found by grepping harder — a legal entity's name, which jurisdiction governs an agreement, a business policy, a subjective judgment call only the person you're building for can actually make. A confident, well-written, wrong answer in this territory is worse than an honest "I don't know — which do you want?" If you can verify it from the code or environment, verify it; if you can't, ask, and say plainly what you checked before asking so it's clear it isn't laziness.

## Phase 2 — Question it before you build it

This is the phase that gets skipped under time pressure, and it's the one that would have caught most of the bugs that ship anyway. Before writing code, actually answer these — in writing, briefly, not just in your head:

- **What's the input space, really?** Not "a file" or "a request" — the empty one, the one with a field missing entirely, the one that's ten times larger than the example you're looking at, the one in a different unit/locale/encoding, the one from a source that's never sent this shape before. If the fix only works on the one example that prompted it, it isn't a fix yet.
- **Is the instruction itself correct?** A request can rest on a factual claim, a convention, or an assumption that's simply wrong — a unit that doesn't actually apply the way it was described, a rule stated slightly differently from how the real system actually works, a "this should always be true" that isn't. Implementing a request exactly as stated is not the goal if the premise is checkable and false. Verify the specific claim before building it in; if it's wrong, say so and explain what's actually true rather than either silently complying with a wrong premise or silently substituting your own guess without mentioning the discrepancy.
- **What would make this fail silently?** A crash is a good outcome — it gets noticed. The dangerous failure mode is a wrong-but-plausible value, a fabricated default that looks like real data, a status that reads "OK" when nothing was actually verified. For every new value your change produces, ask: if this is wrong, will anyone notice, or will it just look like a normal answer?
- **Does the transformation preserve meaning, not just type-check?** Converting, combining, or relabeling a value is only valid if the result still means the kind of thing it claims to mean. Multiplying an index level by an exchange rate, averaging two figures measured over different windows, applying one entity's convention to a different entity by default — these all produce a number that computes cleanly and *looks* like an answer while meaning nothing real. Before writing the math, say out loud what the output is actually supposed to represent, and check the transformation actually produces that.
- **What else reads this value?** A change to one field rarely stays contained to it — it flows into whatever's derived from it, downstream consumers, cached copies, anything that assumed the old shape or unit. Trace forward, not just backward. Grep for every consumer of whatever you're changing before deciding the change is safe.
- **What's the guard, and is it actually tight enough — or too tight?** A validation check that's too loose lets garbage through; one that's too strict rejects genuinely correct real-world values that just happen to be unusual. Don't just add a bound because a bound feels responsible — sanity-check it against a real value (an actual extreme-but-legitimate case, not just the obviously-bad one you're guarding against) before deciding it's right.
- **Write the plan down, short.** A few bullet points: what's changing, why this is the actual root cause, what the blast radius is, how you'll verify it, and what's explicitly *not* in scope for this change. If you can't write this in five lines, you don't understand the change well enough to make it yet.

## Phase 3 — Build it

Now implement, following the plan from Phase 2, matching the codebase's existing style and idioms rather than introducing a new pattern where one already exists. If something you discover while building contradicts the plan — including a plan you yourself proposed earlier, or an approach the user asked for — that's a signal to go back to Phase 1 or 2 and say so explicitly, not to quietly improvise around it or silently ship the original plan anyway.

## Phase 4 — Try to break what you just built

A change that hasn't been attacked hasn't been verified — it's been hoped at. This phase is adversarial on purpose: your job here is to try to prove your own work wrong before someone else does.

- **Run it against real data or real cases, not just the one that prompted the fix.** If you fixed something using one real example, check it against at least one *other* real example — a different source, a different shape, a different scale — to make sure the fix generalizes instead of overfitting to a single case. A fix validated against exactly one input is still mostly a guess.
- **Deliberately try the inputs that would break it.** The empty case, the missing case, the extreme case, the concurrent case, the case where two of your assumptions are both violated at once. If you added a validation guard, try the value exactly on its boundary, and the value just outside it.
- **Run the actual verification suite for this project — all of it, not just what you touched.** Figure out what "the tests" and "the build" actually are here (a README, a CI config file, a package manifest's scripts, a Makefile) rather than assuming a command from a different project. A change that passes its own new test but breaks three existing ones isn't done. If your change could affect a browser, a UI, or anything visual, actually load it and look — a test suite passing is not the same as confirming the thing works the way a person would experience it.
- **Add a regression test that would have caught the original problem**, built from the real case that exposed it where possible — not a clean synthetic example that happens to pass. A test that can't fail isn't testing anything.
- **Review your own diff before committing.** Confirm it contains only the intended change — no incidental noise from running a formatter or generator as a side effect (a regenerated timestamp, an unrelated reformat, a debug print left in), and no unrelated file swept in by a broad `git add`.
- **State what you're still not sure about, and what's explicitly out of scope.** Don't imply total coverage you don't have, and don't let a partial fix pass as a complete one by staying quiet about the boundary. If there's a known gap, a case you didn't test, or a piece the user asked for that you deliberately didn't build yet (because it needed more verification than you had time for, or facts you didn't have), say so plainly rather than letting silence imply it's covered — that's what actually prevents the next round of "wait, I thought you did this part too."

## Some things need a human, not just tests

Passing every check in Phase 4 means the change is *correct* — it doesn't always mean it's ready to ship unattended. Recognize the difference and treat it as a distinct gate, not something Phase 4 automatically clears:

- Content that states a fact about the user's business, legal identity, or obligations (a policy, an agreement, anything with the user's name or business on it) — draft it, verify every fact you can from the code or environment, and then have the actual person read it before it goes live, even if it's technically well-built.
- Anything irreversible, or expensive to reverse, in a way tests can't fully de-risk (a production data migration, a payment-affecting change, deleting something at scale).
- A genuine judgment call where "correct" depends on a preference or a risk tolerance only the user actually holds — surface the decision and the tradeoff, don't make it silently on their behalf.

Shipping something correct-but-unreviewed in one of these categories isn't finishing faster — it's moving the risk from "caught before launch" to "caught after," which is strictly worse even when the underlying work was right.

## When to compress this

Not every change needs the full sequence at full weight — a one-line typo fix or a comment update doesn't need an adversarial verification pass. Use judgment: the depth of this process should scale with the blast radius and subtlety of the change, not apply uniformly to everything. But for anything touching money, extraction or parsing logic, security or auth boundaries, data that persists, or a rule/convention stated as fact — the kind of change where "looks right" and "is right" reliably diverge — run the whole sequence. The cost of the extra five minutes is real; the cost of skipping it and being wrong is almost always bigger, and it's usually paid by someone else, later, with less context than you have right now.
